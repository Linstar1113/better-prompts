# 终版提示词结构与写法

## 一、选择结构

| 任务 | 结构 |
|---|---|
| 一次性、单一交付物、无需解释 | **两段式**：目标 + 输出格式 |
| 多步骤、有约束、要复用 | **四层式**：指令 / 情境 / 参考 / 输出 |
| 原文已足够清楚 | **保留原文**，只补真正缺的一句，并说明为什么 |

绝不为了凑标题编造背景、示例或数据。空层直接删掉。

## 二、四层结构

| 层 | 放什么 | 不放什么 |
|---|---|---|
| 指令 | 任务目标、要做的具体动作、范围边界、权限（能不能改文件/要不要问） | 背景故事、寒暄 |
| 情境 | 用户提供的真实背景、当前状态、输入材料、使用场景 | 编造的行业趋势 |
| 参考 | 用户给的样例/规范/文件，并注明"遵循哪些部分" | 自造的"更好的样例" |
| 输出 | 交付物形态、格式、长度、语言、验收标准 | 与交付物无关的说明 |

## 三、写法规则

1. **目标可验收**：写"输出一张含 A/B/C 三列的表"，不写"深入分析"。
2. **约束写正向**：写"每个卖点不超过 15 字"，少写"不要啰嗦"。
3. **必要条件式化**：用户拿不准的地方写 `如果 X 则 Y，否则 Z`，不写 `[请填写]`。
4. **步骤连续编号**，从 `1.` 开始，每步独占一行，不在步骤里夹解释。
5. **中文终版用平实词**；用户本身是开发者时可以用结构化英文。
6. **不堆砌角色**：不需要"你是世界顶级专家"这类装饰；只在角色真正改变输出时写。
7. **长度与任务匹配**：这条提示词最终要被粘贴进对话，控制在用户一次能读完的范围。
8. **不改用户意图**：用户既要极简又要全覆盖 → 指出来，让用户选，不静默折中。

## 四、终版输出格式

````text
【终版提示词】
```text
<可直接复制粘贴的一整块>
```

【本次改了什么】
- 原话"帮我写个东西" → 明确为"输出 3 条电商详情页首屏卖点文案"
- 补了受众（首屏浏览者）与长度（每条 ≤15 字）
- 输出格式从"写个介绍"改为可直接粘贴的 5 行结构
- 删掉了"高大上"这类不可执行词，换成"短句 + 具体参数"

【仍不确定】
- 品牌调性偏 A 还是 B（终版给了条件式写法，可直接改）

用这条？要改哪句直接说。
````

注意：
- 代码块里**只放提示词本体**，不含你的解释、不含 Markdown 标题。
- "本次改了什么"列 3-5 条，不解释原理、不引来源。
- 没有不确定项就写"无"。

## 五、范例

用户原话："帮我分析一下这个表，看看有什么问题。"

终版提示词：

```text
目标：审查我提供的表格数据，找出其中的问题，输出一份可直接用于修正的清单。

情境：
- 这是一份 <业务类型，如电商月度销售> 明细表，我关心的是 <核心问题，如哪些 SKU 在亏钱>。
- 表格可能存在的典型问题：缺失值、重复行、单位不一致、时间跨度断裂、异常值。

任务：
1. 先给出表格结构摘要（列名、行数、时间范围、每列的空值率）。
2. 按"严重程度从高到低"列出发现的问题，每条给出：问题类型、涉及的具体列或行、判断依据（引用具体数值）。
3. 对每个问题给出可执行的修正建议，并标明该建议是否需要我确认。
4. 最后列出你无法从数据中判断、需要我补充的信息。

输出：
- Markdown，一节一个问题，不超过 800 字。
- 判断依据必须引用表格中的具体数值，不要给笼统结论。
- 不要重排或改写我的原始数据，只出清单。
```

对照：原文的"看看有什么问题"不可验收；终版把"问题"定义成了 5 类可检查项，并给了严重程度排序和证据要求。
