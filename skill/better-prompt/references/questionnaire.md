# 问卷设计：只问阻塞性问题

## 一、缺口维度表

用这张表判断"要问什么"：找出**在原文里没有、且猜错会让交付物整个跑偏**的维度。开发者三域（生图/生文/生成代码）**通用**，域内细则见 §三。

| 维度 | 缺失时的典型症状 | 猜错代价 | 默认优先级 |
|---|---|---|---|
| 目标/交付物 | "帮我写个东西""优化一下" | 极高 | 必问 |
| 生成域判定 | 无法判断是生图、生文还是生成代码 | 极高 | 必做（不一定成题） |
| 受众/使用方 | 没说给谁看、谁来调用 | 高 | 生文必问；代码看调用方 |
| 所在环境/栈 | 没给语言/框架/运行时/平台 | 极高 | 生成代码必问 |
| 接口与边界 | 输入输出、不能动什么未知 | 极高 | 生成代码必问 |
| 输入与素材 | 不知道手头有什么（代码、表、参考图） | 高 | 必问 |
| 输出契约 | 没说格式、长度、分辨率、验收方式 | 高 | 必问 |
| 成功标准 | 无法判断"做完没有" | 中高 | 复杂任务问 |
| 使用场景/平台 | 用在详情页、公众号、CI、生产环境？ | 中高 | 场景差异大时问 |
| 硬约束 | 不能用什么库、不能改什么、截止时间 | 中 | 通常只需复述确认 |
| 语气/风格 | "专业一点""好看" | 低 | **一般不单独问**，映射成特征并标注 |
| 参考样例 | 有没有想模仿的东西 | 低 | 仅在风格要求模糊时问 |

## 二、题面模板

统一格式：

```text
<一句过渡>先确认 N 件事（每题选一个字母，也可以直接用自己的话回答）：

1. <问题>？（<这句话改变什么>）
   A. <选项>（<后果>）
   B. <选项>（<后果>）
   C. <选项>（<后果>）
   D. 都不是，我说明：___
```

规则：

- **≤3 题**；只阻塞进度的才问。
- 选项**互斥且穷尽**到"其他"；每个选项后缀写清后果，让用户不用思考就能选。
- 括号里的"这句话改变什么"必须具体到会改**输出的哪一部分**，不能写"这很重要"。
- 至少给一次"不确定"出口：写成 `不确定（我会用默认值"<X>"，并在终版标【暂定】）`。
- 用户是开发者：术语可以直接用，但只给**能落到输出上**的选项。`不确定（我会用默认值"<X>"，并在终版标【暂定】）` 这条出口每个域都要有。
- 一次问完，不要一问一轮。

### 各维度题面素材

- **交付物** → 最终要拿到什么？（一个脚本 / 一个函数 / 一张图 / 一段文案 / 一份文档）
- **受众/调用方** → 谁看、谁调用？（终端用户 / 团队内部 / 上游服务 / 你自己）
- **输入** → 你手上有什么？（现有代码、日志、表、参考图、接口文档；没有时我要不要先给骨架）
- **输出契约** → 要什么形式？（Markdown / JSON / 纯文本 / 代码块 / 图片比例与尺寸）
- **长度** → 大概多少？（一段 / 一页 / ≤N 字 / ≤N 行 / 单文件）
- **成功标准** → 什么情况下算"能用"？（能直接跑 / 通过现有测试 / 能直接发出去）
- **运行环境** → 在哪跑、什么版本？（见 §三-C）
- **画面与参数** → 主体、构图、比例、风格、控制方式（见 §三-A）

## 三、按生成域的最小问卷

### 三-A 生图

| 维度 | 缺失时的症状 | 猜错代价 | 优先级 |
|---|---|---|---|
| 画面主体 | "画个图""做个海报" | 极高 | 必问 |
| 用途/投放位 | 没说图用在哪（详情页/封面/广告/头像） | 高 | 必问 |
| 构图与比例 | 没给画幅、主体位置、留白 | 高 | 必问 |
| 画面风格 | "好看""高级" | 中高 | 给了模糊词时问 |
| 控制方式 | 文生图 / 参考图 / 局部重绘 / 控图 | 中高 | 有参考图时必须问 |
| 技术参数 | 分辨率、数量、负面内容、模型约束 | 中 | 默认值即可 |

最小问卷：**主体 + 用途 + 构图比例**。其余给默认值（如 1:1、无参考图、通用写实）。

题面素材：
- 主体 → 画面里必须出现什么？（人/物/场景，几个元素）
- 用途 → 这张图最终放哪？（详情页主图 / 封面 / 广告位 / 头像 / 配图）
- 构图 → 横竖比和主体位置？（1:1 居中 / 16:9 主体偏左 / 9:16 竖版满屏）
- 风格 → "高级"具体指？（低饱和极简 / 高对比商业质感 / 胶片颗粒纪实）
- 控制方式 → 有没有参考图或必须保持的元素？（有 → 命名哪些不能变）

### 三-B 生文

| 维度 | 缺失时的症状 | 猜错代价 | 优先级 |
|---|---|---|---|
| 交付物 | "写个东西""写点文案" | 极高 | 必问 |
| 受众 | 没说给谁看 | 高 | 必问 |
| 用途/平台 | 公众号、README、邮件、PRD、周报 | 高 | 必问 |
| 结构 | 没说什么框架、要不要分点 | 中高 | 结构复杂时问 |
| 长度 | 没给字数或篇幅 | 中 | 默认值即可 |
| 语气/风格 | "专业""接地气" | 低 | 一般不单独问，映射成特征 |

最小问卷：**交付物 + 受众 + 用途**。

### 三-B-1 分析报告

维度：输入数据是什么 / 要得到什么结论 / 输出形式（三者互相独立，同时缺失按 2-3 题）。
题面：给我的是什么数据（表、日志、指标）？要回答什么结论？要什么形式（一段话 / 分点清单 / 表格）？

### 三-C 生成代码

| 维度 | 缺失时的症状 | 猜错代价 | 优先级 |
|---|---|---|---|
| 交付物 | "写个脚本""加个功能" | 极高 | 必问 |
| 语言/框架/运行时 | 没说栈和版本 | 极高 | 必问 |
| 接口与边界 | 函数签名、输入输出、调用方未知 | 极高 | 必问 |
| 现有代码与不可动部分 | 没说你手上有什么、不能碰什么 | 高 | 必问 |
| 依赖策略 | 能不能引入第三方库 | 中高 | 默认值即可（默认只用标准库） |
| 错误处理与日志 | 失败时怎么办 | 中 | 默认值即可 |
| 验收方式 | 怎么算完成（能跑通 / 有测试 / 通过 lint） | 中高 | 复杂任务时问 |

题面素材（按变体取用）：

- 交付物 → 最终要拿到什么？（一个脚本 / 一个函数 / 一个接口 / 一次重构后的文件）
- 栈 → 语言、框架、版本？（Python 3.12 + FastAPI / Node 20 + Hono / 纯 Bash）
- 接口 → 输入输出长什么样？（给我一个调用示例或现有签名）
- 边界 → 哪些现有代码不能改？（函数名、返回值、文件结构）
- 依赖 → 能不能装第三方库？（不能 → 只标准库实现）
- 验收 → 怎么判断能用？（能直接跑 / 附单测 / 通过现有 CI）

### 三-C-1 新建

维度：栈与版本 / 接口边界 / 依赖策略（三者互相独立，同时缺失按 2-3 题）。其余给默认值（仅标准库、返回错误而非抛异常、附运行示例）。

### 三-C-2 修改/重构

维度：改什么 / 不改什么（含公开签名是否保持）/ 现有行为基线（三者互相独立，同时缺失按 2-3 题）。
题面：要改哪几处？哪些不能动（签名、返回结构、文件位置）？用什么证明改完的现有行为没变（测试、调用样例）？

### 三-C-3 排错定位

维度：现象与期望 vs 实际 / 复现步骤 / 已排除的可能（三者互相独立，同时缺失按 2-3 题）。
题面：哪个输入触发？期望什么、实际得到什么？已经试过并排除了哪些原因？

### 三-D 混合与跨域

取**主交付物**那一域走上面三节，另一域作为约束写进终版（例如"生成代码 + 附带 README 文档"→ 按三-C 提问，把"同时输出 README"写成输出契约）。

### 三-E 三个生成域之外的开发者任务

按主交付物就近取轴，不要另造一套：

| 任务 | 取轴 |
|---|---|
| 分析数据/日志/指标 | 见 §三-B-1 分析报告变体 |
| 写方案/技术设计 | 目标 + 约束（时间/资源/栈）+ 成功标准 |
| 改已有文本 | 想改什么（更短/更正式/更清楚）+ 必须保留什么 |
| 排错定位 | 见 §三-C-3 排错定位变体 |

## 四、完整示例

> 示例用**生图域**：开发者要给电商详情页做主图。用 3 题展示**题面格式**（选项如何写、后果如何挂）。

> 用户原话："帮我画张产品主图，要高大上一点。"（生图域）

```text
先确认 3 件事（每题选一个字母，也可以直接用自己的话回答）：

1. 画面里必须出现什么？（这决定提示词的主体描述部分）
   A. 单个产品居中，纯净背景（→ 无场景元素，靠光影和材质）
   B. 产品 + 使用场景（→ 需要补环境、光线、人物关系）
   C. 产品 + 卖点文字排版（→ 需要预留文字区，我会给出留白位置）
   D. 都不是，我说明：___

2. 这张图最终放哪？（这决定画幅和视觉重心）
   A. 详情页主图（→ 1:1，主体居中，边缘留安全区）
   B. 站外广告位（→ 16:9，主体偏左，右侧留文案位）
   C. 竖版社媒图（→ 9:16，主体满屏）
   D. 都不是，我说明：___

3. "高大上"你要哪种？（这决定配色、光线和材质描述）
   A. 极简低饱和（→ 灰白背景、柔光、单一材质特写）
   B. 高对比商业质感（→ 深色背景、边缘轮廓光、金属/玻璃材质）
   C. 生活场景质感（→ 自然光、真实台面、浅景深）
   不确定（我会按 B 写，并在终版标【暂定】）
```

**本例问 1 题**：上面 3 题里保留第 3 题（"高大上"最容易跑偏），第 1、2 题改成默认值写进终版（单产品居中 / 1:1 详情页主图）并在交付时点明——用户一句"是场景图、要 16:9"就能推翻。其余参数（分辨率、数量、负面内容）不提问，直接用默认值 +【暂定】。

## 五、反例（不要这样问）

| 反例 | 问题 | 改法 |
|---|---|---|
| "请描述你的目标、受众、语气、长度、格式、约束和成功标准" | 一次抛 7 个维度，用户直接放弃 | 砍到 3 个阻塞项以内 |
| "你希望用什么 persona？需要 few-shot 吗？" | 提示词工程黑话，对开发者也没信息量 | 换成"交付物是什么""要不要给你一个样例照抄" |
| "你为什么要做这个？" | 问动机，不改变输出 | 删掉，或换成"这东西最后用在哪" |
| "你要专业的还是随意的？" | 二选一太窄，且答案是"看情况" | 给 3 个带后果的具体选项 |
| 用户答"不确定"后继续追问 | 制造疲劳 | 用默认值 + 【暂定】标注继续 |
| 把"语气"也做成一道题 | 猜错代价低，占掉提问预算 | 直接给默认值并在终版写明 |
| 生图只问"风格要什么" | 选项空泛、无法执行 | 落成配色/光线/材质，见三-A |
| 生成代码不问"能不能加依赖" | 猜错会给出装不上库的方案 | 默认"只用标准库"并标注 |
| 把"不确定算不算复杂"当成问 3 题的理由 | 判定标准是阻塞维度数，数不出来就是简单任务 | 数不出 ≥2 个独立维度 → 按 0-1 执行 |
